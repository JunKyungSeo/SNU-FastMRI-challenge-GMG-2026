# run4–5 부록 — 다음 run 설계를 위한 레버 조사 (2026-07-08)

run4–5 분석([본편](2026-07-08-run4-5-fullepoch-analysis.md))에 이어, **"다음 run에서 무엇을 바꿀까"**를 코드로 조사한 결과. 속도·용량·최적화·손실 4개 레버를 **각각 실제 코드(file:line)로 확인**했다. (병렬 조사 → 종합.)

> **📌 한 줄 진단:** 모델은 **capacity·loss·memory 문제가 아니라 "덜 훈련됨(underfit) + 고정 LR"** 이다. 그래서 다음 run은 **최적화(cosine LR + epoch)에 예산을 쓰고**, 속도 레버(readout-crop)로 그걸 감당 가능하게 만든다.

---

## 0. 가장 중요한 두 측정값

**① 베이스라인이 드디어 측정됨** (그동안 미측정이던 것):
| | zero-filled | run4 모델 | 모델 기여 |
|---|---|---|---|
| SSIM_full | 0.833 (acc4 0.850 / acc8 0.816) | **0.887** | **+0.053** |
| SSIM_bbox | 0.820 | **0.899** | **+0.079** |

→ **모델은 실제로 학습한다**(zero-filled 대비 +0.05~0.08). "그냥 요동 아니냐"는 기우였음. 단, 보고되던 whole-image "0.882"는 진짜 SSIM_full 0.887을 **과소보고**했고 순위축 bbox 0.899는 아예 안 보였다.

**② 과소적합 신호:** train SSIM ≈ 0.885 ≈ val 0.882 → **train/val 갭 없음 = underfit.** capacity가 아니라 최적화가 병목.

---

## A. 속도 / 메모리

- **gradient checkpointing = ON, 하드코딩**(`latent_recon.py:112`의 `if self.training`), 끄는 플래그 없음. 끄면 +30~50% 시간 회복 가능하나 **OOM 위험** → 9h run에 도박 금물, 유지.
- ⭐ **readout crop 640→384가 SDUM 경로에 안 걸림** — 모델이 **full ~640×368**로 돌고, 끝에서만 384로 center-crop(`adapter.py:59`). crop transform은 구현돼 있으나(`transforms.py:64-78`) **CLI가 없어** 못 켬(`train.py`에 `--readout-crop` 없음, `load_data.py:182` 기본 False).
  - → `--readout-crop` 플래그만 추가하면 **~40% 공간연산·메모리 절감**(9h→~5.4h/epoch, 1차추정), **무손실**(끝의 center-crop과 수학적으로 동일). **가장 큰 레버.**
  - dataloader 튜플 길이 안 늘어남(6-tuple 유지) → 소비부 안 깨짐. `--normalize`는 튜플 늘리니 **같이 켜지 말 것**(어댑터가 이미 self-normalize).
- **VRAM 여유: 미측정.** `probe_oom.py`가 H=384로 하드코딩돼 실제(640) 상황을 **과소평가**. 정확한 수치 원하면 `probe_oom.py:20` H→640 수정 후 측정.

## B. 용량 / config (channels · num-cascades)

- `--num-cascades T`: 독립 cascade T개(`latent_recon.py:308-316`). checkpointing 덕에 **activation peak은 ~T 무관** → **깊이(depth)는 VRAM 싸고 시간 비쌈**(T=5 ~11h/epoch).
- `--channels`: Restormer 폭·레벨(`restormer.py:649,1075`). 넓히면 **per-cascade activation↑**(주 메모리항). `[16,32]→[24,48]` ≈ **+50% activation**.
- **[16,32]×4가 이미 7904/8192 MiB** 사용 중 → **넓히지 마라(OOM 위험)**. 키우려면 **depth(T=5)**가 안전, 단 **`probe_oom` 먼저**(몇 분).
- ⚠️ **1-level `[C]` 실험은 지금 크래시** — `num_blocks/num_heads`가 길이 2로 하드코딩(`config.py:16-17`, `restormer.py:645-647` assert). 돌리려면 ~5줄 수정 필요.
- capacity가 병목이라는 증거 없음(underfit signature) → 넓히는 건 지표 정비 후 probe-gated로만.

## C. 최적화 (LR · epoch · batch)

- ⭐ **LR 스케줄러 없음 — 상수 2e-4** (Task 5는 계획만, `train_part.py`에 scheduler/`import math` 없음). **"빠른 하강 후 정체"의 직접 원인.** cosine으로 0까지 감쇠하면 정체 tail을 뽑는다(SDUM 논문도 2.4e-4 **cosine**).
- **더 많은 epoch:** underfit이라 도움. `-e 1`은 원칙 아니라 9h/epoch 제약 때문. 단 cosine을 **전체 horizon**에 걸어야 효과 큼.
- ⚠️ **resume 없음** — `train()`이 매번 scratch 시작(`start_epoch=0`, `best_val_loss=1.`, load 없음). **epoch 수를 미리 확정**해야 함(중간에 이어서 불가).
- **grad accumulation:** 미구현. 유효배치↑로 batch=1 노이즈를 줄일 수 있으나 불확실 + 시간 안 줆 + 업데이트 수 감소 → **보류**.
- **weight decay** 1e-3 하드코딩. underfit이라 정규화는 병목 아님 → 건드리지 말 것.

## D. 손실 / 지표 (full SSIM 우선)

- **train loss** = whole-image `SSIMLoss`(`loss_function.py:54`, foreground mask 없음). **val metric**도 whole-image인데 **data_range=gt.max()**(`utils.py:39`) — 대회 `SSIM_full`(foreground mask, data_range=attrs['max'])과 **셋 다 다름**.
- 🐛 **`metrics.py`(ssim_full/ssim_bbox/foreground_mask)는 죽은 코드** — 어디서도 호출 안 됨. **그래서 순위 지표를 못 보고 학습해 왔다.**
- 좋은 소식: whole-image(0.882)가 SSIM_full(0.887)을 **0.005 이내**로 추종 → 현재 loss는 SSIM_full의 충실한 대리. **train loss는 whole-image 유지**가 맞음.
- ⭐ **최소 변경(P0):** `validate()`에 **SSIM_full + SSIM_bbox 로깅**(acc4/acc8 분리) 추가(~25줄). val h5의 `attrs['max']`·`attrs['annotations']`를 다시 열어 계산.
  - ⚠️ **`import cv2`가 이 환경에서 깨짐**(libGL) → `foreground_mask`의 cv2 erode/dilate를 **`scipy.ndimage`로 교체** 필요(안 하면 로깅이 import에서 크래시). data_range는 **attrs['max']** 사용(gt.max() 아님).
- **bbox 가중손실 / 병변 슬라이스 oversampling:** 파싱만 되고 **미배선**(`candidates.md`). bbox는 후순위라 **다음 run 범위 밖**.

## 종합 — 추천 다음 run

**진단: 덜 훈련됨 + 고정 LR** → 최적화에 예산, readout-crop으로 예산 확보, 순위 지표 로깅 얹기.

```bash
python train.py --model sdum --num-cascades 4 --channels 16 32 \
  -b 1 -l 2e-4 -e 2 -r 500 --warmup-iters 200 --readout-crop \
  -n sdum_run5 --run-tag run5 -t /root/Data/train/ -v /root/Data/val/
```
- **2 epoch + cosine+warmup** (정체 tail 뽑기) · **--readout-crop** (속도/VRAM 확보) · **SSIM_full/bbox 로깅** (순위 지표 확인)
- 예상 ~10–11h (readout-crop이 ~40% 빨라지면) / 아니면 ~18h

**먼저 할 코드 (전부 P0, 이거 없으면 run 무의미):**
1. `validate()`에 SSIM_full + SSIM_bbox 로깅 (acc4/acc8) — `train_part.py` [~25줄]
2. `metrics.py` cv2 → scipy.ndimage 교체 (이 환경 cv2 깨짐) [~5줄]
3. `train.py`에 `--readout-crop` 플래그 [~1줄]
4. cosine+warmup 스케줄러 배선 (Task 5, 플랜에 코드 있음) [~15줄]

**⚠️ 9h 걸기 전 스모크 테스트(몇 분):** 위 명령에 `--max-iters 30 -e 1 -r 5 --run-tag smoke` → cropped 경로 loss 유한? 스케줄러 step? SSIM_full 로깅 뜸? **실제 s/iter로 ~40% 확인.**

**대안:**
- **5a (짧게, ≤9h):** `-e 1` — 2 epoch 전 싸게 검증(~5.4h).
- **5b (깨끗한 귀속):** `--readout-crop` **빼고** `-e 1` — run4(640)와 해상도 동일하게 두고 **"cosine만으로 정체가 풀리나"**를 confound 없이 확인(~9h).

**정직한 리스크:**
- readout-crop "무손실"은 crop 수학엔 맞지만, scratch 재학습이라 run4와 완전 동일 보장은 아님(LayerNorm 통계 등) → SSIM_full 로깅으로 run4의 0.887과 직접 비교, 나빠지면 뺌.
- ~40% 속도는 1차 추정 → 스모크로 실측.
- OOM 위험 없음([16,32]×4가 이미 640에서 돌고, crop은 메모리를 **줄임**).
- resume 없음 → epoch 수 미리 확정.
